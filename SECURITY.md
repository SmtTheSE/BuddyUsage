# Security

## What BuddyUsage does with your data

Short version: nothing leaves your computer, and there is no server.

| Thing | Where it lives | Leaves the machine? |
| --- | --- | --- |
| Provider sessions (cookies) | One isolated, persistent Electron partition per provider under the app's user-data directory | No. They are sent only to that provider's own domain, by the browser engine, exactly as a normal browser would |
| Your password | Never handled. Sign-in happens on the provider's own page in a real browser window | No |
| Usage numbers | `buddy-usage-cache.json` in the app's user-data directory | No |
| Activity (tokens by project/model/day) | `buddy-usage-activity.json`, derived from the session logs the CLIs already write on this machine | No |
| Settings, including the remote token | `buddy-usage-settings.json` | No |
| Crash or analytics telemetry | Not collected. There is none | No |

The only outbound requests BuddyUsage makes are: the provider usage pages
you connected, and `api.github.com` / `objects.githubusercontent.com` to
check for and download updates.

## The two features that open a door, and how they are bounded

**Phone remote** (off by default) runs a small HTTP listener. With it off,
the listener binds to `127.0.0.1` and serves only hook events from the CLIs
on this machine. With it on, it binds to the LAN so your phone can reach
it. Every URL carries a random 128-bit token; without it the server answers
404 and reveals nothing. "New secret" in Settings revokes old links
immediately. There is no cloud relay: if you want access from outside the
network, use your own VPN (Tailscale or similar).

**Waiting-for-you hooks** add a `curl` line to the CLI's own config
(`~/.claude/settings.json`, `~/.gemini/settings.json`, the `notify` key in
`~/.codex/config.toml`) that posts the event to `127.0.0.1`. Entries are
marked so only ours are touched, Remove restores the file exactly, and
Codex's single `notify` slot keeps your previous value as a comment.

**Agent control** sends signals (`SIGINT`, then `SIGKILL` if forced;
`taskkill` on Windows) to processes owned by your user, and runs each CLI's
own resume command for a nudge. It never runs anything the user did not
ask for.

## Verifying a download

Every release publishes `SHA256SUMS.txt` and a signed build provenance
attestation generated by GitHub's own workflow identity:

```bash
gh attestation verify BuddyUsage-arm64.dmg --repo SmtTheSE/BuddyUsage
shasum -a 256 -c SHA256SUMS.txt --ignore-missing
```

macOS builds are ad-hoc signed; they are not notarized with a paid Apple
Developer ID yet, which is why Gatekeeper asks once. See
[docs/DISTRIBUTION.md](docs/DISTRIBUTION.md).

## Reporting a vulnerability

Please **do not** open a public issue for anything exploitable. Use GitHub's
private reporting (Security → Report a vulnerability) on
[the repository](https://github.com/SmtTheSE/BuddyUsage/security), or email
chris@dvrk.vn. Expect an acknowledgement within a few days; fixes ship as a
patch release with credit unless you prefer otherwise.

## Scope

In scope: anything that lets a third party read your provider sessions or
usage data, reach the local listener without the token, execute code
through a hook or nudge path, or escalate through the updater.
Out of scope: the absence of Apple notarization, and provider pages
changing their wording (that is a parsing bug, not a vulnerability).
